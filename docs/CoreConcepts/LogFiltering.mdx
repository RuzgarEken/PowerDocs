# Log Filtering

:::warning

To enable Power's debug logs, the **POWER_DEBUG** scripting define symbol must be added to your project's **Scripting Define Symbols**.

:::

You can find a video tutorial [▶ here](https://youtu.be/0vtKy50Hpyo?t=355). 

Log filtering is one of Power's core debugging features.

During runtime, Power generates logs from many different systems, including **Actors**, **Processors**, **Stats**, **Effectors**, and more.

Although these logs provide valuable insight into how the runtime flow works, the amount of output can quickly become overwhelming, making it difficult to focus on the information you actually need.

To solve this, Power provides a comprehensive log filtering system that allows you to display logs only from the systems and assets you want to inspect.

To learn how to configure log categories and filters, see **[PowerLogSettings](/docs/Assets/World/Log)**.

## Nested assets follow the caller's log gate

Conditions, adapters, scalers, injectors, custom actors, targeters and targeting filters receive the caller's `canLog` value. A nested Misc asset logs only when the calling Stat, Effect or Processor allows logging **and** its own Misc category/name filter passes. Enabling a condition's Misc filter alone does not force output from an otherwise filtered-out Effect.

Conditional Effects also report each evaluated condition's pass/fail result on their own Effect log channel. This gives a readable state-check result even when the nested condition's Misc logs are filtered out. **All** and **Any** checks short-circuit, so later conditions may not be evaluated.

Custom conditions, adapters, scalers, injectors, actors, targeters and targeting filters accept `bool canLog` in their evaluation methods. Forward this value to nested helpers so they respect the same caller gate. Each asset family's reference page lists its method signatures.
